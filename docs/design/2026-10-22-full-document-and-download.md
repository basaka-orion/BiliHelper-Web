# BiliHelper：完整文档与下载修复设计

日期：2026-10-22  
状态：本地实现审核与真实流程验收中；以下规格不替代当前运行证据。

## 1. 这轮要解决的问题

1. 现有学习笔记每次只分析 20000 字符，并且要求约 600 汉字摘要，无法把一整节视频的内容完整留下来。
2. 网页下载在正式站点上稍大的文件就中断；用户只看到「文件传输中断」。
3. 原产品对「浏览器直连 B 站」和「服务端代理」的能力边界描述不准确。

## 2. 完整文档

### 2.1 单位与来源

- 工作单位仍是「一个视频或一个分 P」。
- 来源优先级：用户粘贴字幕 > 所选平台字幕 > BibiGPT 自动转录 > 当前分 P 音频转写。
- 完整文档模式一次读取当前节的**全部**来源，不再只取 20000 字符。
- 上限 240000 字符；超过时明确报错，提示分段粘贴或使用学习笔记模式，不静默截断。
- 第 2 P 及以后仍不调用第 1 P 的自动转录；BibiGPT 不可用时，使用请求中携带的当前分 P cid 下载该节音频并转写。

### 2.2 分段与整理

- 以字幕 cue 为边界归一化，超长 cue 切分并重新分配全局递增 id。
- 按约 3500 字符、最大 4500 字符切段；每段显式发送 `sourceCues` 与全局 id。
- 每段独立调用一次 `/api/tutorial`（`mode: full-section`），输出详细章节，必须逐项覆盖原文中的定义、命令、参数、路径、步骤、示例、限制和结论，删除寒暄、广告、重复，不得补写。
- 每段完成后立即写入本机保存：来源、总段数、已完成段落。刷新或中断后从下一段继续。
- 全部完成后在前端按顺序合并，生成文档信息、目录、各段正文；不再做一次有损的全篇摘要。
- 最终 `note.evidence` 保存全部 cue，导出时附完整字幕原文（含真实时间码）。

### 2.3 为什么不让服务端一次跑完

- 整节视频可能对应多段、每段都要调用模型；单函数 180 秒不够稳定。
- 前端逐段编排可以在段间保存、停止、续跑，并且每段失败不会丢掉前面已完成的成果。
- 代价是页面需要保持打开；这是现有「刷新后不后台继续」边界的一部分，已有明确提示。


### 2.4 BibiGPT 500 与音频兜底

线上预览出现“自动提取服务访问失败（500）”。BibiGPT 的 OpenAPI 文档明确要求每个请求同时携带：

```
Authorization: Bearer <token>
x-client-type: bibi-cli
```

旧实现只带了 Authorization，现已按官方要求补齐渠道头，并把 `https://api.bibigpt.co` 作为主入口、`https://bibigpt.co` 作为回退。没有同视频请求前后对照证据时，不能认定缺少渠道头就是 500 的根因。

即使 BibiGPT 仍不可用，当前实现还有第二层兜底：

1. 用当前分 P 的 cid 请求 `platform=pc, fnval=16` 的 DASH 播放信息；
2. 从 `dash.audio` 中选择带宽最低、且通过官方媒体域名校验的音轨（单文件不超过 50 MB）；
3. 下载音频后调用 SiliconFlow `/v1/audio/transcriptions`，默认模型 `FunAudioLLM/SenseVoiceSmall`；
4. 把纯文本按句切分成 cue（不伪造时间码），再进入原有的引用与整理流程。

音频转写没有时间码，因此不提供片段回看；但它让没有平台字幕、甚至第 2 P 及以后的视频也可以自动整理。视频超过 1 小时/50 MB 或音频转写失败时，仍引导用户粘贴字幕。

### 2.5 UI

- 「全文整理 / 简短摘要」二选一，按文档保存；新文档与未选过模式的旧文档默认全文整理，保留明确选过的模式和已有笔记。
- 显示第 x/y 段、进度条、停止、继续整理、重新开始。
- 已完成但未全部完成时显示「已完成 n/m 段」，继续整理只处理未完成段。
- 完整文档导出文件名使用「-完整文档.md」，学习笔记仍为「-学习笔记.md」。

## 3. 下载修复

### 3.1 根因

1. 旧 `/api/download` 把最多 40 MiB 的视频完整代理经过 Serverless 函数返回；Vercel 对函数响应体有约 4.5 MB 上限，超过后传输被截断或替换为错误页。
2. 旧前端把非视频响应当 JSON 解析，错误信息丢失，最终只显示「文件传输中断」。
3. 浏览器 JSONP 访问 B 站 `playurl` 时，B 站要求 `Referer: https://www.bilibili.com/`；网页无法伪造该请求头，因此「浏览器直接取播放地址」并不可靠。这同时解释了部分元数据/来源刷新需要回退云端。

### 3.2 新链路

1. 浏览器调用 `/api/download`，`info: true`；服务端用带正确 Referer 的官方 WBI/普通接口取得签名 MP4 地址、大小、实际画质和备用地址，只返回 JSON，不返回视频字节。
2. 浏览器直接 `fetch` 该 CDN 地址（B 站 CDN 返回 `Access-Control-Allow-Origin: *`），显示进度并可停止。
3. 可用的浏览器在初始点击时用 `showSaveFilePicker` 选择位置，最多 700 MiB 流式写盘；其他浏览器最多组装 40 MiB Blob 后保存。取消选择不会偷偷改为内存下载。
4. 云端签名地址及备用线路失败后，为相同分 P 尝试浏览器获取新地址；最后仅当文件 ≤ 4 MiB 才回退到本站代理，否则提示本机 yt-dlp。
5. 多片段、非 MP4、需要登录的视频明确回退到本机下载。

### 3.3 验证

- 当前验收仍在进行：需要在最终候选版本实际保存超过 4.5 MB 的 MP4，并检查文件大小、音视频轨道与时长。此前的文件记录不替代这一轮验证。
- 不经过服务端代理，因此不再受 4.5 MB 响应体上限影响。
- 新增路由测试覆盖 info/direct、超过 4 MiB 的 fallback、多片段、不可信 CDN 地址；新增浏览器媒体地址测试。

## 4. 其他修正

- BibiGPT 请求补齐官方 agent 通道头 `x-client-type: bibi-cli`，并优先使用 `api.bibigpt.co`。
- 新增 SiliconFlow 音频转写兜底，使用当前分 P 的 cid，支持无字幕视频和第 2 P 及以后。
- 打开 B 站视频优先走云端官方 API，浏览器 JSONP 仅作回退，减少无意义的失败等待。
- YouTube 时间戳链接改为 `t=123s`。
- 完整文档和学习笔记的草稿写入做节流，避免流式输出时高频写 localStorage。
- 来源面板支持复制完整原文、下载 SRT（仅在全部 cue 都有真实时间码时）或 TXT。
- 学习笔记导出与完整文档导出使用不同文件名和不同的原文附录标签。
- 课程合集导出：把同一课程中已有笔记的章节按 P 顺序合并；明确只包含已整理章节。
- 本机保存会持久化完整文档进度、来源、已完成段落和 noteMode；恢复时 running 标记为 paused。

## 5. 未做与边界

- 不做整套课程的一键全文整理。第 2 P 及以后优先使用该节字幕；只有核对当前节 CID 后才尝试该节音频转写。
- 不做视频画面理解；完整文档只覆盖字幕/转录文本。
- 不承诺模型输出绝对无遗漏；用完整原文附录作为可核对底稿。
- 不做后台任务：关闭页面后不会继续调用模型，但已完成段落保留。
